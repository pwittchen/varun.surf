# varun.surf CLI - Product & Technical Specification

Status: draft v1 (2026-10-29)
Scope: a command-line client for the existing varun.surf backend, written in Rust and
living in `cli/`. It gives a terminal the same answers the MCP server gives an LLM
(`service/mcp/McpToolService.java`). This document describes **what** to build and
**how**; it contains no implementation.

---

## 1. Goals and non-goals

### Goals

- **Parity with the MCP server.** Every MCP tool has a CLI command that answers the same
  question with the same defaults, limits and wording of errors (section 3).
- Answer the two questions a rider asks from a terminal, fast:
  1. **"When will it blow at this spot?"** - `varun wind jastarnia`
  2. **"Where should I go?"** - `varun windy --country poland`
- Be a good Unix citizen: readable tables on a TTY, plain text when piped, `--json`
  for scripts and `--format md` for pasting into notes or feeding an LLM.
- One static binary per platform, no runtime, starts in well under 100 ms.
- Reuse the existing public API as-is. No backend change is required for v1; optional
  ones are listed in section 11.

### Non-goals

- No business logic duplication beyond what the MCP tools themselves compute: the CLI
  never scrapes Windguru or weather stations and never talks to OpenAI.
- No TUI (full-screen interactive UI) in v1. A `watch` mode is the most interactive it
  gets (section 4.10).
- No paid operations by default. The AI analysis is out of v1 (see 2.2).
- No accounts, no server-side state. Favourites live in a local config file.
- No package-manager distribution in v1 (Homebrew tap, crates.io, winget, AUR) -
  GitHub Release binaries only. Listed as follow-ups in section 10.

## 2. Feature mapping

### 2.1 MCP tool → CLI command

| MCP tool | CLI command | Backend source |
|---|---|---|
| `list_spots` | `varun spots` | `GET /api/v1/spots` (md: `/llms/spots.md`) |
| `get_spot` | `varun spot <SPOT>` | `GET /api/v1/spots/{wgId}` (md: `/llms/spots/{wgId}.md`) |
| `find_spot_by_name` | `varun search <QUERY>` | `GET /api/v1/spots`, filtered client-side |
| `list_countries` | `varun countries` | `GET /api/v1/spots`, grouped client-side (md: `/llms/countries.md`) |
| `get_spots_by_country` | `varun country <SLUG>` (alias `varun spots --country <SLUG>`) | `GET /api/v1/spots` (md: `/llms/countries/{slug}.md`) |
| `get_wind_forecast` | `varun wind <SPOT> [--hours N] [--min-wind K]` | `GET /api/v1/forecast/{wgId}` (md: `/llms/spots/{wgId}/wind.md`) |
| `find_windy_spots` | `varun windy [--min-wind K] [--hours N] [--country C] [--limit L]` | `GET /api/v1/wind?hours=N` + `/api/v1/spots` (md: `/llms/wind.md`) |
| `get_status` | `varun status` | `GET /api/v1/status` (+ `/api/v1/status/forecast`) |

### 2.2 Beyond MCP (CLI-native)

| Feature | v1? | Notes |
|---|---|---|
| Spot argument by name, not only wgId | **Yes** | `varun wind jastarnia` resolves via the spots list (section 4.1) |
| Live conditions (`varun now [SPOT...]`) | **Yes** | The `currentConditions` the spots list already carries; with no argument shows favourites |
| Model selection (`varun spot <SPOT> --model ifs`) | **Yes** | `GET /api/v1/spots/{wgId}/{model}`; `--models` lists `availableModels` |
| Favourites (`varun fav add/rm/ls`) | **Yes** | Local config only (section 6) |
| `watch` mode for `now` / `windy` | **Yes** | Re-render every N seconds, minimum 60 s (live data refreshes once a minute) |
| Shell completions, man page | **Yes** | Generated by clap (section 7) |
| Open spot in browser (`varun open <SPOT>`) | **Yes** | Opens `https://varun.surf/spot/{wgId}` |
| Kite size calculator (`varun kite --weight 80 --wind 18`) | Later | Must stay golden-tested against `src/frontend/js/common/calculator.js`, like the Android port |
| AI analysis (`varun analysis <SPOT>`) | **No** | The only paid call. If ever added: interactive confirmation, refused without a TTY unless `--yes`, never in `watch` |
| Sponsors, metrics, logs, sources | **No** | Operator pages, not rider questions |

## 3. Parity rules (must match the MCP server)

The MCP tools and the `/llms` documents share renderers and constants in
`LlmController`. The CLI mirrors them; when they change, the CLI changes with them.

| Rule | Value | Source |
|---|---|---|
| `wind` default span | 72 h, clamped to `1..forecast length` | `DEFAULT_WIND_FORECAST_HOURS` |
| `wind` `--min-wind` | omitted = every hour; otherwise rows with `round(wind) >= K` | `renderWindForecast` |
| `windy` default floor | 12 kts, minimum 1 | `DEFAULT_MIN_WIND` |
| `windy` default span | 24 h, capped by grid length | `DEFAULT_WINDY_SPOTS_HOURS` |
| `windy` default / max limit | 20 / 100 | `DEFAULT_WINDY_SPOTS_LIMIT`, `MAX_WINDY_SPOTS_LIMIT` |
| `windy` window | first..last hour reaching the floor (not one unbroken run), windy-hour count, peak wind, gusts and direction at peak | `toWindyWindow` |
| `windy` order | peak wind descending, then name | `renderWindySpots` |
| `spot` hourly table | first 24 entries | `HOURLY_FORECAST_LIMIT` |
| Search | case-insensitive substring of the spot name | `findSpotByName` |
| Country match | by name or slug; slug = lowercased name, spaces → hyphens | `LlmController.toSlug` |
| Status sentence | "tracking N spots across M countries. K live weather stations are currently reporting." (singular for 1) | `getStatus` |
| Not-found messages | same text as the MCP tool, adjusted to CLI wording ("Use `varun search`" instead of "Use find_spot_by_name") | `McpToolService` |

**Parity test.** A CI test (section 8.2) runs selected commands with `--format md`
against fixtures and compares them to the matching `/llms` output captured from the same
fixtures, so a drift in defaults is caught rather than discovered.

**Where computation happens.**

- `--format md` fetches the server-rendered `/llms/*.md` document wherever one exists and
  prints it verbatim. That is exact MCP parity for free, needs no session cookie, and is
  what an LLM-pipeline user wants. For `search` and `status` (no `/llms` twin) the
  Markdown is rendered client-side with the MCP tool's layout.
- `table` / `plain` / `json` fetch the JSON API and compute client-side: the windy-spots
  scan, the summary of the windiest hour and kiteable windows. These are small, pure
  functions - unit-tested against the Java implementation's cases.

## 4. Commands

Global form: `varun [GLOBAL OPTIONS] <COMMAND> [ARGS]`.

### 4.0 Global options

| Option | Env | Default | Meaning |
|---|---|---|---|
| `--base-url <URL>` | `VARUN_BASE_URL` | `https://varun.surf` | Backend; `http://localhost:8080` for local dev |
| `--format <table\|plain\|json\|md>` | `VARUN_FORMAT` | `table` on a TTY, `plain` when piped | Output format (section 5) |
| `--json` | | | Shorthand for `--format json` |
| `--lang <en\|pl>` | `VARUN_LANG` | from `LANG`/`LC_ALL`, else `en` | Which `SpotInfo` to show (`spotInfo` / `spotInfoPL`) and CLI messages |
| `--units <kts\|ms\|kmh\|mph\|bft>` | `VARUN_UNITS` | `kts` | Display units only; filters (`--min-wind`) are always in knots, like the API |
| `--tz <local\|spot\|IANA>` | `VARUN_TZ` | `spot` | How forecast hours are shown - see open question Q1 |
| `--no-color` | `NO_COLOR` | colour on TTY | Honour the `NO_COLOR` convention |
| `--no-cache` | | | Bypass the on-disk response cache (section 6.3) |
| `-q`, `--quiet` / `-v`, `--verbose` | `VARUN_LOG` | | `-v` logs requests and timings to stderr |
| `-h`, `--help` / `-V`, `--version` | | | |

### 4.1 Spot argument resolution (`<SPOT>`)

Every command taking `<SPOT>` accepts:

1. An integer → treated as a `wgId`.
2. A `varun.surf/spot/{id}` or Windguru URL → the id is extracted.
3. Anything else → case-insensitive substring search over spot names (with diacritics
   folded, so `mrzezyno` finds Mrzeżyno):
   - exactly one match → used;
   - several matches and an exact (folded) name match among them → that one;
   - otherwise on a TTY an interactive picker (arrow keys, `Esc` cancels); without a
     TTY exit code 4 with the candidate list on stderr.
4. A favourite alias from the config (`varun fav add 500760 --as home`) → `varun wind home`.

### 4.2 `varun spots [--country <C>] [--live]`

All spots grouped by country: name, country, wgId, and (table/plain) live wind when a
station reports it. `--live` keeps only spots with live conditions. Parity: `list_spots`;
with `--country`: `get_spots_by_country`.

### 4.3 `varun spot <SPOT> [--model <KEY>] [--models] [--hours N]`

Full spot details: overview (`SpotInfo`: type, best wind, water temperature, experience,
launch, hazards, season, description), current conditions when present, daily forecast,
first 24 hourly rows (or `--hours`), links (Windguru, Windfinder, ICM, webcam, location,
`https://varun.surf/spot/{wgId}`). `--model` picks a forecast model by
`AvailableModel.key`; `--models` lists the models the spot has. An unknown model key exits
2 and lists the valid ones. Parity: `get_spot`.

Opening a spot through `/api/v1/spots/{id}` triggers server-side model discovery and the
ICM fetch, exactly as the web page does - that is accepted, free load (no paid call).

### 4.4 `varun search <QUERY>`

Matches with name, country, wgId. Exit 3 when nothing matches. Parity:
`find_spot_by_name` (empty query → exit 2 with "Query must not be empty.").

### 4.5 `varun countries`

Countries with at least one spot, spot count each, slug column. Parity: `list_countries`.

### 4.6 `varun country <SLUG>`

Same as `varun spots --country <SLUG>`. Unknown slug → exit 3 with the MCP message
pointing at `varun countries`. Parity: `get_spots_by_country`.

### 4.7 `varun wind <SPOT> [--hours N] [--min-wind K]`

Hour-by-hour wind starting at the current hour: hour, wind, gusts, direction (table adds a
direction arrow and a wind-class colour, section 5.2), plus a summary naming the windiest
hour and the kiteable windows. `--all` adds temperature, rain, cloud, pressure and waves
(the rest of `HourlyForecast`; wave columns hidden when the spot has no wave data).
Parity: `get_wind_forecast`.

### 4.8 `varun windy [--min-wind K] [--hours N] [--country C] [--limit L] [--favorites]`

Spots whose forecast reaches the floor in the window, strongest first: spot, country,
wgId, from, to, windy hours, peak wind, peak gusts, direction at peak. `--favorites`
restricts the scan to favourites. The request asks `/api/v1/wind?hours=<N>` with exactly
the span needed, not the default 120 h. Parity: `find_windy_spots`.

### 4.9 `varun now [SPOT...]`

Live conditions: wind, gusts, direction, temperature, age of the reading. Readings older
than 60 minutes are marked stale (same rule as web and Android). With no argument shows
favourites; with no favourites, the spots with the strongest live wind right now (top 10).

### 4.10 `varun status [--forecast]`

The MCP status sentence plus, in table/json, backend version and uptime. When the forecast
sweep is running (`/api/v1/status/forecast` → `inProgress`) prints its progress, so an
empty forecast right after a deploy explains itself. Parity: `get_status`.

### 4.11 Utility commands

- `varun fav add <SPOT> [--as ALIAS]`, `fav rm <SPOT|ALIAS>`, `fav ls` - local favourites.
- `varun open <SPOT>` - open the spot page in the default browser.
- `varun config [get|set|path|edit]` - read and write the config file.
- `varun completions <bash|zsh|fish|powershell|elvish>` - print a completion script.
- `--watch[=SECONDS]` on `now` and `windy` - clear and re-render; floor 60 s; `Ctrl-C` exits.

### 4.12 Exit codes

| Code | Meaning |
|---|---|
| 0 | Success (including "no spot reaches K kts" - an empty answer is still an answer) |
| 1 | Unexpected error |
| 2 | Usage error (bad flag, empty query, unknown model) |
| 3 | Not found (spot, country, search with no match) |
| 4 | Ambiguous spot name without a TTY |
| 5 | Network error / backend unreachable / 5xx |
| 6 | Rate limited (429 from nginx) - message suggests waiting, no retry storm |

## 5. Output

### 5.1 Formats

- **table** (TTY default): aligned columns, Unicode box/arrow glyphs, colour. Width
  adapts to the terminal; low-priority columns (country, wgId) drop first on narrow ones.
- **plain** (pipe default): tab-separated, no colour, no glyphs, header row - friendly to
  `cut`, `awk`, `sort`.
- **json**: one JSON document on stdout. For pass-through endpoints it is the backend
  payload as received; for computed commands (`windy`, `search`, `countries`, `now`) it
  is a documented CLI schema (`cli/schemas/*.json`), versioned with a top-level
  `"schemaVersion": 1`. Stable across minor CLI versions.
- **md**: the `/llms` document verbatim where one exists, otherwise a client render with
  the MCP tool's layout (section 3).

Errors and diagnostics go to stderr in every format; stdout carries only the answer.

### 5.2 Wind classes and colours

Same thresholds as `src/frontend/js/common/weather.js` (and `android/core/domain`), so a
colour means the same thing everywhere. Unit-test the thresholds against the JS values.
Directions are shown as cardinal plus an arrow pointing where the wind blows to.

### 5.3 Time

`Forecast.date` is a local wall-clock string without a zone (`"Fri 23 Oct 2026 14:00"`);
`CurrentConditions.date` is `dd/MM/yy HH:mm:ss` station-local. Parsing tolerates both and
never fails a command on an unparseable date - it prints the raw string instead.

## 6. Configuration, state and network

### 6.1 Files (XDG / platform dirs via the `directories` crate)

| What | Linux | macOS | Windows |
|---|---|---|---|
| Config `config.toml` | `~/.config/varun/` | `~/Library/Application Support/surf.varun.cli/` | `%APPDATA%\varun\` |
| Cache (responses, session cookie) | `~/.cache/varun/` | `~/Library/Caches/surf.varun.cli/` | `%LOCALAPPDATA%\varun\cache\` |

```toml
base_url = "https://varun.surf"
lang = "en"
units = "kts"
tz = "spot"
format = "table"

[[favorites]]
wg_id = 500760
alias = "home"
```

Precedence: flag > env > config > default. Unknown keys are warned about, not fatal.

### 6.2 Session cookie

- `/api/v1/**` needs the stateless signed `SESSION` cookie. The CLI calls
  `GET /api/v1/session` (204 + `Set-Cookie`) when it has none, stores it in the cache dir
  (file mode 0600), and reuses it until its expiry - the `<epoch>.` prefix of the value -
  is under 1 h away. Never parses or verifies the HMAC.
- On 401: refresh the cookie once and retry the request once; a second 401 is an error
  (exit 5).
- `--format md` uses `/llms/**` and needs no cookie at all.
- `/api/v1/health` is used by `varun status` as a fallback when the session fails.

### 6.3 HTTP

- `reqwest` with `rustls` (no OpenSSL - keeps the binaries static), gzip/brotli on.
- Headers: `User-Agent: varun-cli/<version> (<os>; <arch>)`, `X-Client: varun-cli/<version>`
  (same convention as the Android app's `varun-android/<version>`), `Accept`.
- Timeouts: 5 s connect, 20 s total. One retry with jitter on connect errors and 502/503/504;
  **never** on 429 (exit 6) - the nginx rate limit is what protects the backend.
- On-disk cache of `/api/v1/spots` (~820 spots, the largest payload) for 60 s, so a
  name-resolving command followed by another one does not download it twice. Live
  conditions come from the same payload, which the backend refreshes once a minute, so a
  longer TTL would show stale wind. `--no-cache` bypasses it; a corrupt cache is deleted
  and refetched, never fatal.
- No telemetry, no update check phoning home. `varun --version` prints the version and
  the git commit it was built from.

### 6.4 Client tolerance

As in the Android spec: every response field is optional on the client, unknown fields
are ignored (`#[serde(default)]`, no `deny_unknown_fields`), empty URL strings mean
"absent". The backend evolves independently of CLI releases.

## 7. Technical architecture

### 7.1 Stack

| Concern | Choice |
|---|---|
| Language | Rust, edition 2024, pinned via `cli/rust-toolchain.toml` (latest stable) |
| Arg parsing | `clap` (derive) + `clap_complete` + `clap_mangen` |
| HTTP | `reqwest` (blocking, `rustls-tls`, `gzip`, `brotli`, `json`) - a CLI makes 1-3 requests per run; no async runtime needed |
| JSON | `serde`, `serde_json` |
| Config | `toml`, `directories` |
| Tables / colour | `comfy-table`, `owo-colors` (respects `NO_COLOR`), `terminal_size` |
| Interactive picker | `dialoguer` (only used when stdin/stdout are TTYs) |
| Errors | `thiserror` in the library, `anyhow` at the binary edge, mapped to exit codes |
| Text folding | `unicode-normalization` for diacritic-insensitive search |
| Tests | `assert_cmd`, `predicates`, `insta` (snapshots), `wiremock` or `httpmock` |

Keep the dependency tree small; every new crate needs a reason. `cargo deny` checks
licences and advisories in CI.

### 7.2 Layout

```
cli/
├── SPEC.md
├── README.md                 # install, usage, examples
├── Cargo.toml                # package `varun-cli`, binary `varun`
├── Cargo.lock                # committed (it is a binary)
├── rust-toolchain.toml
├── deny.toml
├── schemas/                  # JSON schemas of the CLI-computed outputs
├── src/
│   ├── main.rs               # clap wiring, exit-code mapping
│   ├── cli.rs                # command and option definitions
│   ├── commands/             # one module per command: spots, spot, search, countries,
│   │                         # country, wind, windy, now, status, fav, open, config, completions
│   ├── api/                  # client, session cookie, cache, DTOs (Spot, Forecast,
│   │                         # HourlyForecast, WindTimeline, Status, ForecastFetchProgress)
│   ├── domain/               # pure logic: spot resolution, windy-window scan, wind summary,
│   │                         # wind classes, units, slug, staleness - no I/O
│   ├── render/               # table, plain, json, md
│   └── config.rs
└── tests/
    ├── fixtures/             # captured /api/v1 and /llms responses
    └── *.rs                  # end-to-end CLI tests against a mock server
```

`domain/` has no I/O and no dependency on `api/` beyond the DTO types, so it is where
the parity logic lives and is tested exhaustively.

### 7.3 Binary size and start-up

Release profile: `lto = "fat"`, `codegen-units = 1`, `strip = true`, `panic = "abort"`,
`opt-level = 3`. Targets: binary under 8 MB, `varun --help` under 20 ms, a cached
`varun wind home` under 300 ms on a normal connection.

## 8. Quality

### 8.1 Testing

- **Unit** (`domain/`): windy-window scan (gaps, nulls, floor, span longer than grid,
  limit clamping, ordering ties), wind summary, slug, diacritic folding, spot resolution
  (exact vs substring vs ambiguous), units, wind classes vs `weather.js`, staleness,
  cookie expiry parsing, config precedence.
- **CLI end-to-end** (`tests/`): each command run against a mock server serving
  `tests/fixtures/`, asserting stdout (`insta` snapshots per format), stderr and exit code.
  Session flow: no cookie → `/api/v1/session` → request; 401 → one refresh → retry; 429 →
  exit 6 without retry.
- **Parity** (section 3): for `spots`, `spot`, `countries`, `country`, `wind`, `windy`,
  compare the client-side Markdown/values against fixture `/llms` documents generated by
  the backend from the same data. Fixtures are regenerated by a small script against a
  local `./gradlew bootRun` and committed.
- Coverage target: 80 % lines (`cargo llvm-cov`), matching the backend's bar.
- No test touches the real `varun.surf`.

### 8.2 Lint

`cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo deny check`.

## 9. CI/CD

### 9.1 Workflow `.github/workflows/cli.yml` (name `CLI`)

Mirrors `android.yml`.

```yaml
on:
  push:
    branches: [ "master" ]
    paths:
      - 'cli/**'
      - '!cli/**/*.md'          # docs only - nothing to build
      - '.github/workflows/cli.yml'
    tags:
      - 'cli-v*'
  pull_request:
    branches: [ "master" ]
    paths:
      - 'cli/**'
      - '!cli/**/*.md'
      - '.github/workflows/cli.yml'
  workflow_dispatch:

defaults:
  run:
    working-directory: cli
```

**Job `build`** (every trigger), `ubuntu-24.04`, `permissions: contents: read`. Like
`ci.yml` and `android.yml`, it is skipped on a branch push whose commit message contains
`#no-deploy` (`if: github.event_name != 'push' || github.ref_type == 'tag' ||
!contains(github.event.head_commit.message, '#no-deploy')`):

1. `actions/checkout`
2. Install toolchain from `rust-toolchain.toml` (`dtolnay/rust-toolchain` or
   `rustup show`), with `rustfmt`, `clippy`
3. `Swatinem/rust-cache` (workspace `cli`)
4. `cargo fmt --check`
5. `cargo clippy --all-targets --locked -- -D warnings`
6. `cargo test --locked`
7. `cargo deny check` (`EmbarkStudios/cargo-deny-action`)
8. `cargo build --release --locked` and upload `target/release/varun` as an artifact
9. On failure: upload test output

A smaller **`check-matrix`** job builds and tests (no release artifacts) on
`macos-latest` and `windows-latest` on pull requests, so platform-specific paths
(config dirs, terminal detection) break in review, not at release.

**Job `release`** - only `if: startsWith(github.ref, 'refs/tags/cli-v')`, `needs: build`,
`permissions: contents: write`. Matrix:

| Target | Runner | Artifact |
|---|---|---|
| `x86_64-unknown-linux-musl` | `ubuntu-24.04` | `varun-<ver>-x86_64-unknown-linux-musl.tar.gz` |
| `aarch64-unknown-linux-musl` | `ubuntu-24.04` (cross / `cargo-zigbuild`) | `.tar.gz` |
| `x86_64-apple-darwin` | `macos-13` (or cross from `macos-latest`) | `.tar.gz` |
| `aarch64-apple-darwin` | `macos-latest` | `.tar.gz` |
| `x86_64-pc-windows-msvc` | `windows-latest` | `.zip` |

Each job:

1. Verifies the tag matches `Cargo.toml`: `${GITHUB_REF_NAME#cli-v}` must equal
   `package.version`, otherwise the job fails (no silently mislabelled binaries).
2. `cargo build --release --locked --target <target>`, with `VARUN_GIT_SHA` baked in for
   `--version`.
3. Packages the binary with `README.md`, `LICENSE`, generated completions and man page.
4. Writes a `.sha256` next to each archive.

A final **`publish`** job (`needs: release`) downloads all archives and creates the GitHub
Release `cli-vX.Y.Z` (`softprops/action-gh-release` or `gh release create`) titled
`varun CLI X.Y.Z`, body taken from the matching section of `cli/RELEASES.md`, with all
archives and a combined `SHA256SUMS`. Marked as not "latest", so the backend's `v*`
releases keep the "Latest" badge on the repo page.

### 9.2 Interaction with existing workflows

- `ci.yml`: add `'cli/**'` and `'.github/workflows/cli.yml'` to both `paths-ignore`
  lists, as is done for `android/**`, so a CLI change does not build the backend.
- `cd.yml`: triggers on `v*` tags and its release job selects tags with `grep '^v'`;
  `cli-v*` tags match neither, so no change is needed. Verify when implementing.
- `deps.yml`: a follow-up job running `cargo update` in `cli/` and verifying with the
  `build` job steps before pushing, like the Android job. Not required for v1.

### 9.3 Releasing (developer flow)

1. Bump `version` in `cli/Cargo.toml`, add a section to `cli/RELEASES.md`.
2. Commit, then `git tag cli-vX.Y.Z && git push origin cli-vX.Y.Z`.
3. The `CLI` workflow builds, tests and publishes the release. Versions follow SemVer;
   the JSON output schema only changes incompatibly on a major bump.

## 11. Optional backend changes (not required for v1)

- `GET /llms/search.md?q=` and `GET /llms/status.md` would make `--format md` server-rendered for
  every command and remove the last client-side Markdown renderers.
- A `Cache-Control: max-age` on `/api/v1/spots` (instead of `no-store`) would let the client cache
  honour the server's freshness rather than a fixed 60 s.
- Counting `X-Client: varun-cli/*` in `SpotsControllerMetrics` would show CLI usage on `/metrics`.

---

## 12. Open questions

- **Q1 - time zones.** `Forecast.date` carries no zone. Show hours as served ("spot time") or
  convert to the user's zone? Converting needs the spot's zone, which the API does not expose
  (the same open question as the Android spec's Q1). Default to `spot` until it is resolved.
- **Q2 - binary name.** `varun` is short and memorable; check it does not clash with a common
  package on Homebrew/AUR before the first public release.
- **Q3 - JSON for pass-through commands.** Pass the backend payload through (cheap, but its shape is
  the backend's) or always wrap it in the versioned CLI schema (stable, more code)? Draft: pass
  through for `spot`/`status`, CLI schema for computed commands.

## 13. Acceptance criteria (v1)

- Every MCP tool in section 2.1 has a command whose `--format md` output equals the matching
  `/llms` document, and whose defaults/limits match section 3.
- `varun wind <name>` and `varun windy` work without any configuration on a fresh machine.
- All commands produce valid `--json`, documented in `cli/schemas/`.
- Piped output contains no ANSI codes; `NO_COLOR` is honoured.
- Exit codes follow section 4.12; network failures never panic.
- A push touching `cli/**` (non-docs) runs the `CLI` workflow and only it; a `cli-vX.Y.Z` tag
  publishes a GitHub Release with five platform archives and checksums.
- Test coverage at least 80 %; `clippy -D warnings` clean.
